# 4. Компетенции и рекомендации

Исследовательская часть платформы (требования F-50, F-51): задания связаны с компетенциями, у студента формируется профиль подтверждённых компетенций, а лента дополняется объяснимыми рекомендациями.

## 4.1 Компетенции и теги

|                   | Теги                            | Компетенции                                     |
| ----------------- | ------------------------------- | ----------------------------------------------- |
| Что описывают     | технологии и предметную область | навык, который развивает задание                |
| Кто создаёт       | работодатель, свободный ввод    | платформа, фиксированный справочник             |
| Язык              | как ввели                       | два названия: `name_ru`, `name_en`              |
| Сколько у задания | до 10                           | до 5 — «фокус» задания, а не перечисление всего |
| Для чего          | фильтры ленты, похожие задания  | профиль студента, рекомендации                  |

Справочник — таблица `competencies` (`code` — стабильный ключ, не меняется при переименовании). Связи: `_TaskCompetencies` (задание ↔ компетенция) и `_StudentInterests` (студент ↔ компетенции, которые он хочет развивать).

## 4.2 Профиль подтверждённых компетенций

Профиль **не хранится**, а вычисляется из принятых решений (`entities/competency/api/competencyQueries.ts`). Компетенцию подтверждает работодатель, принимая решение по заданию, к которому она привязана. Поэтому профиль не может разойтись с историей решений и его нельзя «накрутить» отдельно.

Для каждой компетенции считаются:

- **баллы** — сумма сложностей принятых заданий (простое — 1, среднее — 2, сложное — 3);
- **уровень** по баллам: базовый (< 3), уверенный (3–5), продвинутый (≥ 6) — одно сложное задание весит как три простых, а «продвинутый» требует нескольких заданий;
- число подтверждающих решений и средняя оценка.

Условия ИС на профиль не влияют: NDA скрывает результат работы, но не сам факт навыка.

Профиль виден в кабинете студента и на странице портфолио (работодателю, преподавателю, администратору).

## 4.3 Рекомендации заданий

Задача: из опубликованных заданий выбрать те, что полезны студенту, и **объяснить почему**. Используется контентный подход со взвешенными признаками — он прозрачен, работает с первого дня (без накопленной статистики, в отличие от коллаборативной фильтрации) и его легко описать и проверить.

**Кандидаты:** опубликованные задания с открытым сроком, с которыми студент ещё не взаимодействовал (нет в избранном, нет заявки и решения); 200 самых свежих.

**Сигналы о студенте:**

| Сигнал                | Откуда                                                                              |
| --------------------- | ----------------------------------------------------------------------------------- |
| Интересы              | студент сам отмечает до 5 компетенций в кабинете                                    |
| Подтверждённые навыки | компетенции принятых решений                                                        |
| Знакомые теги         | теги заданий из избранного, заявок и решений                                        |
| Целевая сложность     | новичку — 1; иначе максимум из принятых, при средней оценке ≥ 4.5 — на ступень выше |

**Оценка задания** (`entities/task/lib/rankTasks.ts`, чистая функция):

| Признак                                   | Вес          | Причина в интерфейсе            |
| ----------------------------------------- | ------------ | ------------------------------- |
| Компетенция из интересов                  | +3 за каждую | «Ваш интерес: …»                |
| Компетенция уже подтверждена (не интерес) | +1 за каждую | «Развивает вашу компетенцию: …» |
| Совпавший тег из истории (не больше 3)    | +1 за каждый | «Похоже на ваши задания: …»     |
| Сложность равна целевой                   | +1           | «Подходит по уровню»            |
| Сложность выше целевой                    | −2           | —                               |

Сложность сама по себе не повод рекомендовать: если нет ни одной содержательной причины (интерес, навык, тег), задание не попадает в выдачу. Итог сортируется по сумме, при равенстве — по дате публикации; показываются первые 6.

**Почему так:**

- интерес — явное желание студента, поэтому у него самый большой вес; история — неявный сигнал;
- ограничение на число тегов не даёт заданию с длинным списком тегов всегда побеждать;
- штраф за сложность не убирает задание совсем: при сильном интересе студент всё равно его увидит;
- причины показываются под карточкой, и студент может повлиять на выдачу, поменяв интересы.

**Развитие:** когда накопится статистика, веса можно подбирать по данным (какие рекомендации приводят к заявке и принятому решению), а признаки дополнить коллаборативными («студенты с похожим профилем выполняли…»). Функция ранжирования отделена от запросов к БД, поэтому её можно заменить, не трогая остальной код.
